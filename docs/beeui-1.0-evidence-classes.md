# BeeUI 1.0 Evidence Classes

Use precise evidence language in issues, PRs, reviews, docs and release reports.

## Deterministic contract evidence

Examples: unit/component tests, deterministic schedulers, type/API tests, registry graph tests, token lifecycle/semantic-consumption checks.

Proves only the contract exercised by those tests.

## Browser interaction evidence

Real browser execution such as Playwright keyboard/pointer/focus flows and automated accessibility checks.

Does not prove native runtime behavior.

## Visual evidence

Rendered screenshot/image comparison on a named platform/viewport/theme/state.

Does not prove interaction correctness by itself.

## Bundle/compile evidence

Metro/Web bundle, Expo prebuild, Android native compile, iOS native compile.

Proves build/toolchain compatibility for the tested graph; does not prove interactive runtime behavior.

## Native runtime evidence

App launched and representative interaction executed on a named iOS Simulator, Android Emulator, or physical device with exact build/SHA.

Simulator/emulator evidence must be described as such and must not be generalized to untested physical-device-only behavior.

## Assistive-technology evidence

VoiceOver/TalkBack/manual or supported automated interaction on a named build/runtime.

Do not describe limited checks as accessibility certification.

## Clean-consumer evidence

Packed/source-owned artifact installed into an independent consumer without monorepo fallback, then typechecked/bundled/compiled/runtime-tested as required.

## Performance evidence

Measurements generated by the accepted benchmark harness with environment/sample metadata and a stated noise/budget methodology.

## Release evidence

One immutable candidate manifest ties exact SHA, package/CLI tarballs and hashes, docs/llms build, compatibility report, demo build identity and all required gate results together.

## Rule

Always state the strongest evidence class actually obtained, never the strongest evidence class desired.
