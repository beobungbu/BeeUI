# BeeUI performance methodology & baseline report (R5.8, #186)

This is the durable authority for BeeUI performance claims. It states what is
measured, how, on what environment, how to reproduce it, the current numbers
with interpretation, the regression policy that gates them, the noise this
lane actually produces, and — as important — what BeeUI does **not** claim.
If a perf claim about BeeUI cannot be traced to a number in this report (or a
reproduction of it), do not make the claim.

Methodology of record: `docs/benchmark-harness.md`. This report does not
restate that document's mechanics; it publishes the numbers it produces and
interprets them. Regression budgets derived from these numbers are documented
in `docs/benchmark-harness.md`'s "Regression budgets" section and enforced by
`pnpm bench:web` / `pnpm bench:native` (timing overhead-ratio budgets) and
`pnpm bench:budget` (package/bundle footprint budgets).

## Evidence class

Per `docs/beeui-1.0-evidence-classes.md`, every number below is **performance
evidence**: "measurements generated by the accepted benchmark harness with
environment/sample metadata and a stated noise/budget methodology." Numbers
produced through `apps/showcase`'s Jest + `@testing-library/react-native`
lane are additionally **deterministic-contract evidence** (same class as this
repo's own component tests) — not browser-interaction or native-runtime
evidence. None of the numbers below are native-device or real-Metro-bundle
measurements unless explicitly labeled as such.

## How to reproduce

```bash
pnpm bench:web                # timing: variant-class-resolution, Table render/update
pnpm bench:native              # timing: native lane (deferred off-device, see below)
pnpm bench:components          # timing: component render/commit, overlay latency, theme runtime
pnpm bench:footprint           # bytes: packed tarball + clean-consumer bundle contribution
pnpm bench:budget               # bytes: footprint numbers vs. recorded regression budgets
pnpm bench:test                 # unit tests for the harness + budget-evaluator logic
```

## 1. Package/bundle footprint (#183 baseline)

Full numbers and interpretation: `docs/bundle-footprint-baseline.md`. Headline
figures (packed gzip, real release-ready `dist/` layout):

| Package | Packed (gzip) |
| --- | ---: |
| `@beeui/core` | 25.1 KiB |
| `@beeui/tokens` | 97.3 KiB |
| `@beeui/ui` | 495.3 KiB |

Clean-consumer bundle contribution (esbuild proxy over real built output,
peers externalized), Web:

| Scenario | Gzip |
| --- | ---: |
| `full-barrel` (today's only import path) | 52.3 KiB |
| `single-component-direct` (Button, hypothetical granular subpath) | 10.2 KiB |
| `table-direct` | 11.0 KiB |
| `sheet-direct` | 17.6 KiB |

**Interpretation.** Importing a single `Button` through today's one `"."`
barrel export costs 50.8 KiB gzip — within 2.4% of importing the whole
library (52.3 KiB) — because nothing prunes the barrel's ~90 other named
exports. A hypothetical direct/granular import of the same `Button` is 10.2
KiB: an ~80% reduction. This is the measured evidence #184's granular-export
decision consumes; it is not itself a decision to add subpath exports.

**Optional dependency cost, separated from BeeUI-owned bytes.** `sheet-direct`
on Web (17.6 KiB) never references `@gorhom/bottom-sheet` or
`react-native-reanimated` as externals (Web resolves `sheet.web.js`, which
does not import them). The native-extension-priority proxy for the same
scenario (16.4 KiB) DOES reference `@gorhom/bottom-sheet` +
`react-native-reanimated` + `react-native-teleport` as externals — real peer
cost a native consumer's bundler will pull in, correctly kept out of BeeUI's
own reported bytes. `tailwind-merge` (~105.6 KB pre-minify input) is the one
non-trivial always-bundled third-party dependency across every scenario
(`@beeui/core`'s `cn()` utility); see the baseline doc for the full
attribution.

**Regression budget.** `scripts/benchmark/footprint-budgets.mjs`, enforced by
`pnpm bench:budget` — see `docs/benchmark-harness.md`'s "Regression budgets"
section for the warn/fail tolerance policy.

## 2. Table render/update stress and scale (#168/#180 baseline)

| Scenario | Rows | Median render pass |
| --- | --- | ---: |
| `web/table-render-100` | 100 | ~0.073ms |
| `web/table-render-500` | 500 | ~0.36ms |

Both are the real `cn()`-based per-row/per-cell Web hot path
(`packages/ui/src/components/table.web.tsx`), not a fabricated end-to-end
render number (`scripts/benchmark/scenarios/web/table-render.mjs`'s own
comments explain why this proxy is the honest shape for a pure-Node harness).
Full numbers and consumer-facing guidance:
`apps/docs/src/content/docs/components/table.md`'s Performance section.

**Interpretation.** Both scale points measure comfortably under a 16ms frame
budget, confirming ADR-007's Option B: no default/adapter virtualization is
currently justified. `cn()`'s real `twMerge` conflict resolution costs
consistently ~8-9x a naive string-concatenation baseline at both scales (the
ratio tracks per-call cost, not row count) — budgeted at `maxOverheadRatio:
15` so a real regression in `cn()`/`twMerge` itself would be caught. Table
does not memoize rows by default (`apps/showcase/__tests__/table-performance.test.tsx`
proves a plain `rows.map(...)` re-invokes every row's render function on a
sibling's selection change); an optimized/memoized consumer's single-row
update floor (`web/table-row-update`) measures at ~1.2% of a full 100-row
recompute, budgeted at `maxOverheadRatio: 0.2` so a regression that makes a
single-row update scale with total row count would fail the check.

## 3. Component render/commit stress (#180 baseline, component lane)

Real BeeUI component trees mounted/updated through `@testing-library/react-native`
Jest lane (`apps/showcase/__tests__/perf-render-commit.test.tsx`). Selected
medians from this report's recorded run (full set in
`.artifacts/benchmark/web-component-77804df70e4c.json`, gitignored —
reproduce with `pnpm bench:components`):

| Scenario | Median | CV |
| --- | ---: | ---: |
| Mount 100 Buttons | 7.8ms | 43% |
| Mount 500 Buttons | 45.7ms | 37% |
| Update 100 Buttons (variant toggle) | 6.1ms | 45% |
| Mount 100 ListItems | 11.3ms | 23% |
| Update 100 ListItems (content change) | 8.8ms | 119% |
| Mount 500 ListItems | 60.1ms | 37% |
| Mount an open Select, 120 options | 69.5ms | 40% |
| Mount 24 closed Selects | 22.0ms | 219% |
| Mount a 100-row Table | 16.2ms | 34% |
| Mount a 500-row Table | 93.4ms | 41% |
| Mount a Calendar month grid | 4.7ms | 60% |
| Toast queue churn at capacity | 0.35ms | 17% |

**Interpretation.** These are single-workload measurements with no baseline
pair, so read the median as an order-of-magnitude cost for that tree shape on
this class of host, not a portable millisecond guarantee — see "Known noise"
below for why the coefficient of variation (CV) is large enough on several
rows (up to 219%) that a tighter reading would be dishonest. No absolute-
millisecond regression budget is set on this lane; see
"Regression policy" below for why.

## 4. Overlay open-latency (#181 baseline)

`apps/showcase/__tests__/perf-overlay-latency.test.tsx` drives real
mount/open/close cycles through `waitFor` for every anchored-overlay
component:

| Scenario | Median | CV |
| --- | ---: | ---: |
| Dialog, cold | 2.11ms | 9% |
| Dialog, warm | 1.33ms | 9% |
| DropdownMenu, cold | 5.19ms | 183% |
| DropdownMenu, warm | 2.80ms | 35% |
| Popover, cold | 2.24ms | 38% |
| Popover, warm | 1.46ms | 13% |
| Select, cold | 8.03ms | 12% |
| Select, warm | 2.17ms | 6% |
| Sheet, cold (default motion) | 1.94ms | 47% |
| Sheet, cold (reduced motion) | 1.56ms | 84% |
| Sheet, warm (reduced motion) | 1.16ms | 78% |
| Tooltip, cold (focus channel) | 0.96ms | 6% |
| Tooltip, warm (focus channel) | 0.51ms | 32% |

**Interpretation.** Every overlay opens well within a single frame on this
host, cold or warm; "warm" (steady-state) is consistently cheaper than "cold"
(first-open), as expected for JIT/inline-cache warm-up. The CV column is the
important number here: `dropdown-menu-open-cold` swings up to 183% run over
run on this shared dev host — reading its median alone without that context
would overstate precision the measurement does not have.

## 5. Theme runtime performance (#182 baseline)

`apps/showcase/__tests__/perf-theme-runtime.test.tsx`:

| Scenario | Median | CV |
| --- | ---: | ---: |
| Apply a density mode | 0.0020ms | 6% |
| `getBeeToken` imperative read | 0.0065ms | 22% |
| Global light/dark switch (`Uniwind.setTheme`) | 0.057ms | 228% |
| High-contrast switch | 0.038ms | 26% |
| Runtime CSS-variable override | 0.038ms | 7% |
| Scoped Bee/Violet theme switch | 0.139ms | 10% |
| `useBeeToken` live-updating read | 0.038ms | 14% |

**Interpretation.** All theme-runtime operations cost a small fraction of a
millisecond — no theme operation is a plausible frame-budget risk on its own.
`useBeeToken`'s live-updating hook read (0.038ms) costs roughly 6x
`getBeeToken`'s bare imperative snapshot read (0.0065ms) in this run, which is
the expected shape of React re-render + resolve overhead on top of the same
underlying lookup; this pair does not yet carry a regression budget (see
below) because the two are recorded as separate scenario ids, not a single
candidate/baseline pair. `global-light-dark-switch`'s 228% CV is the most
extreme outlier this report recorded — a single GC pause or scheduler
hiccup during a sub-millisecond measurement window dominates the number, per
"Known noise" below.

## 6. Native lane

`native/list-render` and `native/table-render-100`/`-500` are registered and
callable but **deferred**: this harness runs off-device (a local dev box, or
a JS-only CI job), so per `docs/benchmark-harness.md`'s Web-vs-native
methodology there is no honest native-runtime number to report here. The
runner records `status: 'deferred'` with a note explaining why rather than
fabricating a device timing. An on-device runner (iOS Simulator / Android
Emulator / device) is required to produce a real `measured` native result.

## Regression policy

See `docs/benchmark-harness.md`'s "Regression budgets" section for the full
policy. Summary:

- **Timing scenarios with a controlled baseline pair** (Table's `cn()` vs.
  naive-concat, and its row-update floor vs. full recompute) are gated by a
  self-normalizing `maxOverheadRatio`, enforced by `pnpm bench:web` /
  `pnpm bench:native` (non-zero exit on a budgeted scenario over budget).
- **Package/bundle footprint bytes** are gated by a percentage-of-baseline,
  two-tier (warn 10% / fail 20%) budget, enforced by `pnpm bench:budget`.
- **Component render/commit, overlay-latency and theme-runtime scenarios with
  no baseline pair** are measured and published (this report) but are **not**
  budget-gated today — see "Known noise" below for the evidence behind that
  decision.

## Known noise

The component lane (render/commit, overlay latency, theme runtime) runs
inside Jest + `@testing-library/react-native` on a shared dev host with no
isolation from other processes, GC pauses, or thermal throttling, and many of
its scenarios measure sub-millisecond or low-single-digit-millisecond work —
small enough that a single scheduler hiccup can dominate a sample. This
report's own recorded run shows coefficients of variation from 6% (tight) to
228% (`global-light-dark-switch`) and 219% (`selects-24-mount`) across
scenarios in the SAME run on the SAME host. This is exactly the "brittle
absolute-millisecond gate on a noisy runner" case #185 warns against, and is
the concrete evidence behind this report's decision not to add one for this
lane. Trend/regression consumers should compare medians only across low-CV
runs of the same scenario, on the same class of host, per
`docs/benchmark-harness.md`'s sampling-strategy section — never a single
run's absolute number in isolation.

## What this report does not claim

- **Not a cross-framework comparison.** No number here is compared against
  React Native Paper, Tamagui, NativeBase, shadcn/ui, or any other UI
  library. The harness's own baseline workloads compare two implementations
  of the SAME output (e.g. `cn()`-resolution vs. naive concatenation) as a
  controlled reference, never a rival framework's architecture
  (`docs/benchmark-harness.md`, "Overhead vs a baseline").
- **Not "faster than every framework," "zero-cost," or similarly unqualified
  marketing language.** Every number above is scoped to a named host,
  environment, and evidence class, and none of them is a claim about any
  other library's performance.
- **Not a native-device measurement.** Every number in this report except the
  package/bundle footprint bytes is deterministic-contract or Node-hosted
  Web evidence; native timings are `deferred` (see §6) until an on-device
  runner supplies them.
- **Not a production-app measurement.** See §7 — there is no BeeUI
  production demo yet.
- **Not a promise that these exact millisecond numbers reproduce on your
  hardware.** Timing numbers are host-relative; only the package/bundle
  footprint bytes are expected to reproduce exactly given the same source and
  toolchain versions.

## Updating this report

Re-run the reproduce commands above, update the tables and environment block
with the new run's provenance, and — if a package/scenario's real footprint
intentionally grew — update `docs/bundle-footprint-baseline.md` and
`scripts/benchmark/footprint-budgets.mjs` in the same PR (see
`docs/benchmark-harness.md`'s "Updating a budget"). Do not edit the numbers
in this report without an actual reproduction run backing them.
