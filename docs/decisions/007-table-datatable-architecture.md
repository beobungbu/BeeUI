# ADR-007: Table / DataTable product architecture

Status: Accepted

## Context

BeeUI 1.0's roadmap (`docs/roadmap.md`, R4E, `#164 → #165 → (#166 + #167 + #168) → #169 → #170`) requires a hard-1.0 Table/DataTable surface: "stable, accessible, responsive and performance-bounded" (`docs/roadmap.md:421`), and a production Table/DataTable flow is already committed for the demo (`docs/roadmap.md:333`, #260 "searchable/filterable Table/DataTable flow"). No Table implementation exists yet in `packages/ui/src/components/`. This ADR is the architecture decision `#165`–`#170` execute against; it ships no code (doc-only, per `#164`'s DoD).

BeeUI has established, accepted precedents this decision must reuse rather than duplicate:

- **Compositional primitives over data-driven "smart" components.** `ListGroup`/`ListGroupHeader`/`ListItem` (`packages/ui/src/components/list-group.tsx`), `Accordion`, `Tabs`, and `Pagination`/`PaginationItem` (`packages/ui/src/components/pagination.tsx`) are all composed from small typed subcomponents the caller assembles with JSX children — none of them accept a `data`/`columns`/`items` array and render internally. `docs/architecture.md` states BeeUI "should make common application UI fast to compose without forcing applications to inherit a particular router, backend, state library, form library" — an array-driven `DataTable` that owns column definitions would start pulling row-rendering, key extraction, and eventually data-shape assumptions into BeeUI, which is exactly the ownership this ADR must avoid per the issue's explicit non-goals.
- **Controlled-only state discipline.** `docs/architecture.md`'s "Controlled interaction contract" — `Checkbox`, `Radio`, `RadioGroup`, `Switch`, `Tabs`, `SegmentedControl` are deliberately controlled; "BeeUI does not invent hidden uncontrolled state for these APIs." `Pagination` takes `page`/`pageCount`/`onPageChange` as caller-owned state and only renders from it (`pagination.tsx:22-29`).
- **Local positional context instead of global state.** `ListGroup` shares one boolean `React.createContext` scoped to its own subtree so `ListItem` can tell it is "inside a list" without a store (`list-group.tsx:7-14`, `ListGroupMembershipContext`). ADR-004 documents the same "no second global state engine" invariant for direction; `useDirection()` (`packages/ui/src/components/use-direction.ts`) is the single stateless resolver every component that needs JS-level direction calls, and is explicitly the contract "any future anchored-overlay-geometry component (Table, Calendar)... needing JS-level direction resolution" must reuse rather than reinvent (ADR-004, "Implementation consequences").
- **Platform-diverging files behind one import path.** `overlay-transport.web.tsx` / `overlay-transport.native.tsx` (`packages/ui/src/components/`) already prove the accepted mechanism for "Web and native implementations differ, consumers import one path" — Metro/bundler platform extension resolution, not a runtime `Platform.OS` branch inside one file, when the divergence is structural (different host elements/APIs) rather than a value computation.
- **Density is a shared token axis, not a component-local invention.** `docs/density.md` ships `compact`/`comfortable`/`spacious` density tokens already covering "list-row height/gap" and "form-field gap" as canonical density-sensitive metric groups (`densityMetricVariables`, `$extensions["com.beeui"].densityAxis`). Table row sizing is architecturally the same category of metric.
- **The benchmark harness never fabricates numbers.** `scripts/benchmark/scenarios/native/list-render.mjs` is a placeholder proving the pattern this ADR's performance section must follow: register a real scenario, return a `deferred` result off-device, and let an on-device/browser runner (or #180/#185) produce the actual number — never invent one in an ADR or in code.
- **Accessibility evidence is layered, not a single gate.** `docs/web-accessibility-audit.md` (axe-core over real Showcase scenarios), `docs/beeui-1.0-evidence-classes.md` (browser-interaction vs. native-assistive-technology vs. deterministic-contract evidence), and `docs/agent-execution-contract.md`'s ban on "claim[ing] browser/compile/simulator evidence proves a stronger runtime/device class than was actually tested" all constrain how this ADR may state Web-vs-native accessibility parity: as an intent plus a verification plan, not as an unverified assertion.

React Native has no native `<table>` element and no first-class win from reusing DOM table semantics; React Native Web renders `View`/`Text` as generic `<div>`/`<span>` by default. Meanwhile a real Web `<table>` (or ARIA `grid`) gets substantial free assistive-technology behavior (row/column announcement, header association) that a `View`-based tree does not. This is the concrete fork the issue's "Web semantic table/grid primitives vs native accessible composition behind one coherent API" line names, and it must be decided here rather than left to `#166`/`#167` to each guess independently.

## Constraints

- **Non-goal (hard, from #164/#114):** BeeUI does not own fetching, backend/query state, or server pagination for Table. `Pagination` already exists as the caller-facing page-control primitive; Table must not duplicate or wrap a second pagination/query-state concern.
- **Non-goal (hard):** sorting/filtering/selection *state* is caller-controlled or exposed only through narrow, stateless headless helpers — no internal sort/filter/selection store, no context-based "TableProvider" holding row data.
- **Non-goal:** this ADR does not design a spreadsheet/grid-editing experience (arrow-key cell navigation, in-cell editing, roving tabindex across arbitrary cells). Nothing in `#164`–`#170`'s scope or `docs/roadmap.md` R4E requires it; inventing it would be scope creep the execution contract's "Scope discipline" forbids.
- **Reuse, don't duplicate:** direction resolution reuses `useDirection()` (ADR-004); row/cell size metrics reuse the existing density token axis (`docs/density.md`) rather than a parallel Table-only sizing system; platform divergence reuses the existing `.web.tsx`/default-file-extension mechanism (`overlay-transport.*`) rather than a new per-component abstraction; performance evidence reuses the `#179` benchmark harness (`scripts/benchmark`) rather than a bespoke Table-only measurement script.
- **Package boundary:** Table is a `@beeui/ui` component family. It must not introduce a new `@beeui/core` geometry layer (no anchored-overlay-style positioning is needed for a static/scrolling table) and must not add a runtime dependency for virtualization unless `#168` produces concrete evidence a default (non-virtualized) render fails an accepted scale target.
- **Accessibility is correctness, not polish** (`docs/agent-execution-contract.md:78`): Web and native must each reach the best semantics their platform actually supports, verified by that platform's own evidence class (`docs/web-accessibility-audit.md` for Web, native VoiceOver/TalkBack evidence per `docs/beeui-1.0-evidence-classes.md` for native) — this ADR may not assert native accessibility-role parity with Web that `#167` has not yet verified.
- **RTL/logical direction, dynamic type, high contrast, reduced motion** apply to Table exactly as they do to every other BeeUI component (`docs/agent-execution-contract.md:78-79`, `docs/dynamic-type.md`); Table must not disable font scaling to protect a fixed layout, per `docs/dynamic-type.md`'s hard rule.
- **Distribution:** any new Table registry entry must resolve through the existing repository-local registry/CLI (`docs/registry-cli.md`) using existing transitive entries (`core-cn`, `text`, `box`, `checkbox`, `overlay-runtime` is not needed since Table has no anchored overlay) wherever possible, and must not leak `workspace:*`/private imports.
- **Non-goal:** this ADR does not itself add a new density token metric group, a new registry entry, a new benchmark scenario file, or a new a11y scenario — those are `#165`/`#168`/`#170`'s implementation tasks. This ADR only decides the contract those tasks must satisfy.

## Options considered

### Table anatomy/API ownership

#### Option A — Single data-driven `DataTable` component (`columns` + `data` props, internal row rendering)

- **Design summary**: One component accepts a `columns: ColumnDef[]` array (key, header, optional `render`/`accessor`, optional `sortable`) and a `data: T[]` array, and renders `<thead>`/`<tbody>` internally from those arrays, similar to TanStack Table / MUI DataTable's declarative-config shape.
- **Benefits**: least JSX for simple cases; centralizes sort/render logic in one place; a natural home for later virtualization since BeeUI would own the full row list.
- **Risks/tradeoffs**: `ColumnDef`/`accessor` typing is exactly the kind of generic-data-shape ownership `docs/architecture.md`'s "fast to compose without forcing applications to inherit a particular... state library" and the issue's explicit non-goal ("BeeUI does not own fetching/backend/query state") warn against — a config-driven column API inevitably grows `accessorFn`, `cell` render-prop, `meta`, sort comparators, and filter predicates over time (this is exactly what TanStack Table's own surface looks like), each a new implicit contract BeeUI would have to stabilize and version. It also breaks BeeUI's established compositional pattern used by every other structural component (`ListGroup`, `Accordion`, `Tabs`, `Pagination`) — those all accept JSX children, not data arrays.
- **Web/iOS/Android implications**: an internal-rendering component makes the Web-real-`<table>`-vs-native-View fork *harder* to isolate cleanly, because the same internal row-mapping code must branch per platform instead of the platform fork living once at the primitive-element level.
- **Dependency/package/registry impact**: larger public API surface (generic `ColumnDef<T>` type parameters), higher registry/versioning risk since the config shape is much more likely to need a breaking revision post-1.0 than a small set of structural primitives.
- **Accessibility/RTL/large-text/reduced-motion impact**: harder to audit — a11y correctness would depend on the internal renderer choosing correct semantics per cell type, rather than the caller directly controlling markup via explicit subcomponents.
- **Migration/semver impact**: a generic `ColumnDef<T>` shape is high semver risk; adding one sortable/filterable feature tends to require a breaking or additive-but-messy config field.
- **Rejected**: contradicts the issue's explicit non-goals and BeeUI's established compositional precedent without a countervailing requirement forcing it.

#### Option B — Composable primitive family (`Table`, `TableCaption`, `TableHeader`, `TableBody`, `TableFooter`, `TableRow`, `TableHead`, `TableCell`), no data/column ownership

- **Design summary**: Mirror the shape of `ListGroup`/`ListGroupHeader`/`ListItem` and `Pagination`/`PaginationItem`: small typed subcomponents the caller composes with plain JSX, mapping their own array of domain rows to `<TableRow>`/`<TableCell>` themselves (`{items.map(item => <TableRow key={item.id}>...</TableRow>)}`), exactly as an application already does for any other list. `TableHead` accepts optional controlled sort-affordance props (`sortDirection?: 'ascending' | 'descending' | 'none'`, `onSortChange?: () => void`) mirroring the controlled-callback discipline `Checkbox`/`Tabs` already use — Table stores no sort state itself, it only renders the caller-supplied indicator and calls back on interaction. Row selection reuses the existing `Checkbox` component directly inside a `TableCell`/`TableHead`; the caller owns the selected-id set exactly as it would for any other list of checkboxes, so Table needs no bespoke selection state at all.
- **Benefits**: zero new data-shape ownership; matches every other BeeUI structural component's precedent exactly; keeps the public API small and stable (subcomponents' props barely need to change once shipped, unlike a growing `ColumnDef`); the Web/native platform fork can live once, at the primitive-element level (`Table`/`TableRow`/`TableCell` internals), not duplicated across a rendering loop; naturally composes with `Pagination` (already shipped) for paging controls, with no Table-owned pagination concept needed.
- **Risks/tradeoffs**: more call-site JSX for simple cases (caller writes the `.map()` loop itself) — acceptable, matches `ListGroup`'s existing tradeoff, and is the same amount of code an application already writes for any list.
- **Web/iOS/Android implications**: `Table`/`TableHeader`/`TableBody`/`TableFooter`/`TableRow`/`TableHead`/`TableCell` each get a `.web.tsx` file rendering the real semantic HTML element (`<table>`, `<thead>`, `<tbody>`, `<tfoot>`, `<tr>`, `<th>`, `<td>`) and a default (native) file rendering `View`/`Pressable`-based composition with RN accessibility props — see "Platform rendering strategy" below.
- **Dependency/package/registry impact**: small, additive registry entries; new registry dependency edges onto `checkbox`, `text`, `box`, `core-cn`, `use-direction`; no new runtime dependency.
- **Accessibility/RTL/large-text/reduced-motion impact**: each subcomponent's a11y contract is scoped and auditable per-element, same granularity as `ListGroup`/`ListItem`'s existing WAI-ARIA "Required Context Role" handling (`list-group.tsx:7-13`).
- **Migration/semver impact**: low — adding a new optional prop to `TableHead`/`TableCell` is additive; there is no generic config object to version.
- **Testing/runtime evidence required**: deterministic contract tests per subcomponent (roles/names/states), Web axe scenario, native VoiceOver/TalkBack evidence, RTL column-order test, dynamic-type stress test — same evidence classes every other BeeUI component already uses.
- **Selected.**

#### Option C — Headless/render-prop table engine (BeeUI ships only hooks; no visual subcomponents)

- **Design summary**: BeeUI exports only stateless helper hooks/functions (sort-toggle cycling, `aria-sort` value mapping, column-label registration) and zero rendering components; the application builds 100% of the visual table itself.
- **Benefits**: maximal caller flexibility; zero a11y-markup ownership risk for BeeUI.
- **Risks/tradeoffs**: fails the issue's explicit requirement that "BeeUI owns semantic table layout, row/cell composition, a11y, density and responsive presentation" — a pure-headless engine owns none of those; every consuming application would reimplement the Web-`<table>`-vs-native-composition fork and its a11y semantics independently, which is precisely the duplicated-per-consumer work BeeUI exists to prevent (mirrors the reasoning ADR-004 used to reject "no ambient read at all").
- **Web/iOS/Android implications**: none provided by BeeUI at all — regresses relative to what the issue asks BeeUI to own.
- **Rejected**: does not satisfy the issue's ownership requirement; the narrow-headless-helpers language in the issue applies to *sort/filter/selection state*, not to table layout/composition/a11y, which the issue explicitly assigns to BeeUI.

### Platform rendering strategy (Web semantic table vs. native accessible composition)

#### Option A — Uniform `View`-based tree on both platforms, ARIA-grid-style roles simulated everywhere via RN's `accessibilityRole`

- **Design summary**: One shared (non-platform-split) implementation using `View`/`Pressable`/`Text`, applying whatever RN `accessibilityRole` values exist to approximate table semantics identically on Web (via React Native Web's role mapping) and native.
- **Benefits**: one file per subcomponent, no `.web.tsx` split to maintain.
- **Risks/tradeoffs**: gives up the free, mature, and widely-supported real HTML `<table>` semantics on Web (row/column announcement, header association, native browser find-in-page/print/select-all-in-cell behavior) in exchange for an RN accessibility-role approximation whose exact table/grid/row/cell role coverage varies by RN version and is not something this ADR can verify without the RN type surface actually pinned in this repo (`0.86.2` per `docs/compatibility-matrix.md`) — asserting a specific role name here without that verification would violate the execution contract's evidence-honesty rule. Even where a `grid`-like role exists, it typically implies an ARIA-grid *interaction* contract (arrow-key cell navigation) that this ADR explicitly does not want to build (see Constraints, spreadsheet non-goal) — adopting the role without the interaction is itself an accessibility defect (announcing grid navigability that doesn't exist).
- **Web/iOS/Android implications**: strictly worse Web accessibility than Option B for the same implementation cost, and still leaves native accessibility unverified.
- **Rejected**: worse Web outcome than Option B at equal cost, and lets the native question remain equally uninvestigated.

#### Option B — Platform-diverging semantic composition: real HTML table elements on Web, RN accessible `View`/`Text` composition on native, unified behind one import path per subcomponent

- **Design summary**: Reuse the exact mechanism `overlay-transport.web.tsx`/`overlay-transport.native.tsx` already established. Each Table subcomponent gets a `.web.tsx` implementation rendering the real host element (`<table>`, `<thead>`, `<tbody>`, `<tfoot>`, `<tr>`, `<th scope="col">`/`<th scope="row">`, `<td>`, `<caption>`) via React Native Web's ability to render arbitrary host elements, and a default (native) implementation composing `View`/`Text`/`Pressable` with the best RN accessibility props available, verified empirically rather than assumed. Both implementations accept the identical public props (`Table`, `TableRow`, `TableCell`, etc. keep one prop contract); only the rendered host output differs, exactly as `overlay-transport`'s two files share one call-site contract. A header cell's sort affordance renders as a `<button>`-equivalent (`Pressable`) inside the header cell on both platforms, so no custom roving-tabindex grid navigation is required — normal tab order reaches it like any other interactive control.
- **Benefits**: Web gets full native `<table>` assistive-technology support "for free" (this is the entire reason HTML tables exist); native gets a composition whose actual accessibility characteristics are established empirically by `#167` rather than guessed; the public API is identical either way, so a caller's JSX does not change per platform, matching "behind one coherent API" from the issue; reuses an already-accepted BeeUI mechanism rather than inventing a new one.
- **Risks/tradeoffs**: native table-like semantics have a real, currently-unverified gap (no native "this is a table/row/cell" AT announcement equivalent to HTML by default); this ADR closes that gap architecturally by requiring `#167` to produce native VoiceOver/TalkBack evidence and to encode row/column context into each cell's accessible name/label where RN has no dedicated structural role, rather than by asserting a specific RN role mapping here without evidence.
- **Web/iOS/Android implications**: exactly the fork the issue names ("Web semantic table/grid primitives vs native accessible composition behind one coherent API") — this option is the literal answer to that line.
- **Dependency/package/registry impact**: two files per subcomponent (as `overlay-transport` already does), registered once in the registry entry's `files` array (`docs/registry-cli.md`'s schema already supports multiple `files` per registry item).
- **Accessibility/RTL/large-text/reduced-motion impact**: Web path gains real `<table>` AT semantics plus BeeUI's existing dynamic-type/rem-based typography contract (`docs/dynamic-type.md`) unchanged; native path is verified, not assumed, by `#167`.
- **Migration/semver impact**: none (net-new component).
- **Testing/runtime evidence required**: Web axe scenario addition (`docs/web-accessibility-audit.md`'s "Extension mechanism"), Playwright semantic/keyboard check that `<table>`/`<th scope>`/`aria-sort` render correctly (`#166`), native VoiceOver/TalkBack evidence for row/column/header announcement (`#167`).
- **Selected.**

#### Option C — Real `<table>` on Web, but native falls back to a non-tabular alternative (e.g., tell native consumers to use `ListGroup` instead of shipping a native Table at all)

- **Design summary**: Ship the Web-only semantic table; native applications compose `ListGroup`/`ListItem` themselves for equivalent data.
- **Benefits**: avoids the native accessibility-verification burden entirely.
- **Risks/tradeoffs**: directly contradicts `docs/roadmap.md:421` ("Table/DataTable stable, accessible, responsive **and performance-bounded**" is listed as a flat 1.0 exit criterion, not a Web-only one) and the R4E chain's explicit `#167` "Table native rendering and accessibility policy" child issue, which presupposes a native Table exists.
- **Rejected**: contradicts an already-accepted roadmap commitment; not this ADR's call to unilaterally narrow.

### Responsive mobile strategy (horizontal scroll vs. stacked/card)

#### Option A — Horizontal scroll only, no stacked/card mode

- **Design summary**: `Table` always renders as a normal table; on narrow viewports the caller (or a default wrapper `Table` provides) scrolls it horizontally.
- **Benefits**: simplest; preserves literal column alignment and header association at every width; requires no per-cell label metadata; matches plain HTML table behavior wrapped in `overflow-x: auto` on Web and a horizontal `ScrollView` on native.
- **Risks/tradeoffs**: horizontal scroll is a well-documented poor mobile UX for wide tables with many columns (users must discover and perform a sideways gesture to see data past the fold) — a real limitation `docs/roadmap.md`'s own "searchable/filterable Table/DataTable flow" (#260) production-demo target is likely to hit on a narrow viewport with a realistic column count.
- **Rejected as the *only* strategy**: does not satisfy the issue's requirement that the responsive strategy be an explicit choice between horizontal scroll *and* stacked/card, not a default that ignores the alternative.

#### Option B — Horizontal scroll as the owned default; explicit opt-in stacked/card presentation as a second BeeUI-owned mode, using a lightweight column-label registration context

- **Design summary**: `Table` owns two responsive presentations, selected by one explicit prop (illustrative name: `Table`'s `layout?: 'scroll' | 'stacked'`, default `'scroll'`):
  1. **`scroll` (default)**: `Table`'s Web file wraps its `<table>` in a horizontally scrollable container (`overflow-x: auto`); the native file wraps the row `View`s in a horizontal `ScrollView`. This requires no additional API and is what every caller gets with zero extra wiring — BeeUI owns this responsive behavior outright, satisfying "BeeUI owns... responsive presentation" for the default case.
  2. **`stacked` (explicit opt-in)**: when the caller sets `layout="stacked"` (typically driven by the caller's own breakpoint/viewport decision, since BeeUI does not own viewport-breakpoint policy any more than it owns routing), `TableRow` instead renders as a card-like block and each `TableCell` renders as a `label: value` pair. The label is resolved the same way `ListGroup`'s `ListGroupMembershipContext` resolves list membership (`list-group.tsx:7-14`): `TableHeader`'s `TableHead` cells register their column index → header text into one small, subtree-scoped React context as they render (mirroring, not duplicating, the existing local-positional-context pattern), and each `TableCell` looks up its own column index in that registry unless the caller supplies an explicit `label` override prop (needed when a header is an icon or otherwise not plain text). No global store, no state persisted across renders beyond the current render's registration — this is the same "local context describing tree position" shape `ListGroup` already uses, not a new state-engine category.
- **Benefits**: satisfies the issue's explicit requirement that the strategy be a real choice, not a single default; keeps BeeUI, not the caller, responsible for both renderings of the same composed rows (the caller does not duplicate its `.map()` loop per breakpoint); reuses an already-accepted local-context mechanism instead of inventing one; the `label` override keeps the door open for non-text headers without forcing every caller to supply redundant labels for the common (plain-text header) case.
- **Risks/tradeoffs**: `stacked` mode changes the rendered DOM/element shape significantly (no longer a `<table>` on Web in that mode — it becomes a labelled block list, which is the *correct* semantic choice for a card layout; a `<table>` forced into a single-column narrow layout is not itself more accessible than a labelled block list). This is an intentional, documented tradeoff: `stacked` is not "the same table visually rearranged," it is a second, equally-real presentation of the same rows.
- **Web/iOS/Android implications**: `stacked` mode's implementation is symmetric across platforms (both become a block/card composition, closer to `ListGroup`'s existing shape) — likely lower net new platform-fork risk than `scroll` mode.
- **Dependency/package/registry impact**: no new runtime dependency; the column-label registry context is internal, not a new public export, matching ADR-004's precedent of keeping the direction resolver internal by default.
- **Accessibility/RTL/large-text/reduced-motion impact**: `stacked` mode is likely to *improve* large-text/narrow-viewport accessibility relative to a forced-narrow `<table>`, since each value gets an explicit adjacent label rather than relying on remembering a column header scrolled out of view; RTL column order in `scroll` mode follows `useDirection()` (logical start/end column order, per ADR-004) rather than a hardcoded physical left-to-right assumption.
- **Migration/semver impact**: none (net-new, `layout` defaults to today's only behavior).
- **Testing/runtime evidence required**: deterministic test that `stacked` mode's inferred label matches the corresponding `TableHead`'s text; deterministic test that an explicit `TableCell` `label` overrides inference; visual/Playwright evidence for both `scroll` and `stacked` presentations; native runtime evidence that horizontal `ScrollView` and stacked `View` composition both behave correctly under VoiceOver/TalkBack swipe navigation.
- **Selected.**

#### Option C — Automatic, un-opted-in breakpoint-driven switching (Table itself measures viewport/container width and silently switches layout)

- **Design summary**: `Table` measures its own rendered width (or `useWindowDimensions()`) and automatically switches between `scroll` and `stacked` without a caller-provided prop.
- **Benefits**: zero caller wiring for the "correct" behavior at every width.
- **Risks/tradeoffs**: BeeUI does not currently own a breakpoint/viewport-policy authority anywhere in the codebase (Showcase's own 960px desktop breakpoint and 760px preview canvas, `docs/architecture.md:56`, are Showcase-local policy, not a `@beeui/ui` API), and inventing one here as a Table-only side effect would be exactly the kind of "reusable unrelated gap opportunistically redesigned" the execution contract's "Scope discipline" forbids. It also silently changes rendered semantics based on live measurement, which is harder to test deterministically (no fixed input controls the output) than an explicit prop, and harder for a caller to reason about when embedding `Table` inside a container narrower than the viewport (window-width heuristics would pick the wrong layout).
- **Rejected**: introduces an unscoped viewport-policy authority and non-deterministic-by-default behavior without evidence it is needed; Option B already gives BeeUI ownership of both renderings while keeping the width *decision* an explicit, caller-supplied, deterministic input — consistent with how `Popover`/`DropdownMenu`/`Select` keep `direction` as an explicit override seam over ambient magic (ADR-004).

### Virtualization

#### Option A — Ship virtualization by default for every `Table`

- **Design summary**: `TableBody` always windows its rows (e.g., wraps native rows in `FlatList`-equivalent windowing; Web rows in a JS windowing library).
- **Benefits**: uniform performance ceiling regardless of row count.
- **Risks/tradeoffs**: forces a nested-scroll-container/sticky-header architecture on every consumer even for the common small-table case; on Web, virtualizing real `<table>` rows breaks native browser row-count/announcement semantics unless `aria-rowcount`/`aria-rowindex` are added and column widths are fixed (a real, nontrivial cost); adds a real or effective new dependency before any evidence (`#168`) shows it is required — violates the issue's explicit "Virtualization is adapter/optional unless an accepted scale target requires it."
- **Rejected**: contradicts the issue's explicit instruction and adds unconditional cost with no supporting evidence yet.

#### Option B — No default virtualization; adapter/optional escape hatch gated by `#168`'s accepted scale-target evidence

- **Design summary**: `TableBody` renders every supplied `TableRow` child directly (no windowing) by default. If and only if `#168`'s benchmark evidence (via the `#179` harness, `scripts/benchmark`) shows the accepted 100/500-row scale envelope (`docs/roadmap.md`'s "100/500-row performance envelope") is not met by default rendering, a virtualization *adapter* is added as an explicit opt-in (illustrative: a separate composition helper or `virtualized` prop building on a platform-appropriate windowing primitive — `FlatList`/similar on native; a Web windowing approach that preserves `aria-rowcount`/`aria-rowindex` and fixed/explicit column widths for `<table>` row-count semantics), not a forced default.
- **Benefits**: matches the issue's explicit instruction exactly; keeps the common case (dozens to a few hundred rows in a typical product screen, per #260's own scope) simple and fully semantic; defers the real engineering cost of virtualization until evidence, not speculation, justifies it.
- **Web/iOS/Android implications**: default path is symmetric and simple on both platforms; the escape hatch, if ever needed, is platform-appropriate rather than one-size-fits-all.
- **Dependency/package/registry impact**: no new dependency now; any future virtualization adapter would be evaluated and justified independently against `#168`'s evidence, following the same "narrow the promise, don't document hope" discipline `docs/compatibility-matrix.md` already applies to dependency claims.
- **Accessibility/RTL/large-text/reduced-motion impact**: none regressed by default (no windowing means no AT-row-count gap to solve today); the escape hatch's own future ADR-or-implementation-note must resolve the `aria-rowcount`/`aria-rowindex`/fixed-column-width requirement before shipping, called out here so `#168` does not have to rediscover it.
- **Migration/semver impact**: additive only if/when added.
- **Testing/runtime evidence required**: `#168` must produce real (not fabricated) 100-row and 500-row measurements via the `#179` harness before any virtualization decision is made either way.
- **Selected.**

## Decision

BeeUI 1.0 adopts, for Table/DataTable:

1. **API ownership — Option B (composable primitive family).** `Table`, `TableCaption`, `TableHeader`, `TableBody`, `TableFooter`, `TableRow`, `TableHead`, `TableCell` are typed, composable subcomponents the caller assembles with JSX, exactly like `ListGroup`/`ListGroupHeader`/`ListItem` and `Pagination`/`PaginationItem`. BeeUI does not accept a `columns`/`data` array and does not render rows internally from one. `#165` ("core anatomy/API") owns finalizing exact prop names/types under this contract.
2. **State boundaries.** Table stores no fetching/query/pagination/sort/filter/selection state. Paging composes with the existing `Pagination` component (caller owns `page`); sort affordance on `TableHead` is a controlled `sortDirection`/`onSortChange` pair the caller drives, mirroring the `Checkbox`/`Tabs` controlled-callback discipline already documented in `docs/architecture.md`'s "Controlled interaction contract"; row selection reuses the existing `Checkbox` component with the caller owning the selected-id set. Any headless helper BeeUI ships for sort/filter/selection (e.g., a pure sort-toggle-cycling function, an `aria-sort` value mapper) must be a stateless pure function/hook with no internal store — never a hidden state engine.
3. **Platform rendering strategy — Option B (platform-diverging semantic composition, one shared prop contract).** Each subcomponent gets a `.web.tsx` file rendering the real HTML table element it corresponds to (`<table>`, `<thead>`, `<tbody>`, `<tfoot>`, `<tr>`, `<th scope="col"|"row">`, `<td>`, `<caption>`) and a default (native) file composing `View`/`Text`/`Pressable`, reusing the exact `overlay-transport.web.tsx`/`overlay-transport.native.tsx` file-splitting mechanism already accepted in this codebase. Both files honor one identical public prop contract per subcomponent. Native's exact accessibility-role/label strategy is decided empirically by `#167` against this codebase's actual pinned RN version (`0.86.2`, `docs/compatibility-matrix.md`) rather than asserted here; at minimum, native cells must convey row/column context in their accessible name/label where RN has no dedicated structural role, verified by real VoiceOver/TalkBack evidence, not assumed parity with Web.
4. **Responsive mobile strategy — Option B (owned default + explicit opt-in second mode).** `Table` defaults to horizontal-scroll presentation (Web: `overflow-x` scroll container around a real `<table>`; native: horizontal `ScrollView`) with zero required caller wiring. An explicit opt-in (illustrative: `layout="stacked"`) switches `TableRow`/`TableCell` to a card/label-value presentation for narrow viewports, using a `ListGroup`-style local column-label registration context (`TableHead` registers column index → label; `TableCell` looks its label up unless given an explicit override) so the caller does not duplicate its row-mapping loop per breakpoint. BeeUI does not invent a breakpoint/viewport-measurement authority; the caller supplies the `layout` value from whatever breakpoint policy it already uses (matching how `direction` stays an explicit override seam per ADR-004).
5. **Virtualization — Option B (adapter/optional, evidence-gated).** No default windowing. `TableBody` renders every supplied row directly. A virtualization adapter is added only if `#168`'s real, harness-measured (`#179`/`scripts/benchmark`) 100/500-row evidence shows the default un-windowed render fails the accepted scale envelope; if added, the Web variant must preserve `aria-rowcount`/`aria-rowindex` and fixed/explicit column widths so windowing does not silently break `<table>` row-count semantics for assistive technology.
6. **Density.** Table row height/gap and cell padding are density-token-driven (`docs/density.md`'s `compact`/`comfortable`/`spacious` axis), starting from the existing `list-row`-equivalent metrics as the baseline; whether a dedicated `table-row` density metric group (via the existing `densityAxis: true` mechanism, `scripts/generate-tokens.mjs`) is needed instead is `#165`'s implementation decision based on whether list-row metrics prove sufficient, not a new token-schema decision made by this ADR.
7. **Direction/RTL.** Column order and any directional glyph (e.g., a sort-direction indicator that has a logical rather than physical meaning) resolve through the existing `useDirection()` resolver (ADR-004) — Table does not add a second direction read.

## Rejected alternatives

- **Data-driven `columns`+`data` `DataTable` (Option A, anatomy)**: rejected — contradicts the issue's explicit fetching/query-state non-goal in spirit (a growing `ColumnDef` config is exactly the kind of implicit state/rendering contract BeeUI keeps out of its own hands) and breaks the compositional precedent every other BeeUI structural component follows.
- **Headless-only engine, no visual subcomponents (Option C, anatomy)**: rejected — fails the issue's explicit instruction that BeeUI owns semantic layout/composition/a11y/density/responsive presentation, which a pure-headless engine provides none of.
- **Uniform `View`-based tree with simulated ARIA-grid roles on both platforms (Option A, platform strategy)**: rejected — gives up real, mature HTML `<table>` semantics on Web for an unverified RN role approximation, and risks announcing grid-style keyboard navigability BeeUI does not implement.
- **Web-only Table, no native Table (Option C, platform strategy)**: rejected — contradicts the already-accepted roadmap 1.0 exit criterion and the existing `#167` "native rendering and accessibility policy" child issue.
- **Horizontal-scroll-only, no stacked/card mode (Option A, responsive strategy)**: rejected — the issue explicitly requires the responsive strategy to be a real, explicit choice between horizontal scroll and stacked/card, not a single default.
- **Automatic, un-opted-in breakpoint-driven layout switching (Option C, responsive strategy)**: rejected — would require inventing a new, currently-nonexistent BeeUI viewport-breakpoint-policy authority as an unscoped side effect of this ADR, and trades deterministic caller-driven behavior for width-measurement heuristics.
- **Default virtualization for every Table (Option A, virtualization)**: rejected — contradicts the issue's explicit "adapter/optional unless an accepted scale target requires it" instruction and imposes real architectural cost (nested scroll containers, `<table>` AT row-count risk) before any evidence justifies it.

## Implementation consequences

- **`#165` (core anatomy/API)** implements `Table`/`TableCaption`/`TableHeader`/`TableBody`/`TableFooter`/`TableRow`/`TableHead`/`TableCell` under this ADR's ownership/state-boundary contract, decides the exact density-metric-group question (reuse `list-row` vs. add `table-row`), and defines the exact `layout`/stacked-mode prop names and the column-label registration context, following the `ListGroupMembershipContext` shape.
- **`#166` (Web semantics/keyboard)** implements the `.web.tsx` files rendering real HTML table elements, wires `aria-sort` on `<th>` and a `<button>`-equivalent sort trigger inside it, confirms normal tab order reaches all interactive cells without a custom roving-tabindex grid pattern (per this ADR's explicit non-goal), and extends `docs/web-accessibility-audit.md`'s `a11yScenarios` with a Table scenario.
- **`#167` (native rendering/a11y)** implements the default (native) files, empirically establishes and documents the actual RN accessibility-role/label strategy for row/column/cell context against the pinned RN version, and produces the VoiceOver/TalkBack evidence this ADR defers rather than asserts.
- **`#168` (performance/scale acceptance)** registers real Table scenarios under `scripts/benchmark/scenarios/{web,native}/` (following the `native/list-render.mjs` deferred-until-on-device pattern) for the 100-row and 500-row envelope, and is the sole source of the virtualization go/no-go decision this ADR gates on evidence rather than deciding today. Regression budgets themselves remain `#185`'s responsibility per `docs/roadmap.md` R5.
- **`#169` (production patterns/visual acceptance)** exercises both `scroll` and `stacked` responsive presentations and feeds the production-demo `#260` "searchable/filterable Table/DataTable flow" (search/filter state stays application-owned per this ADR's state-boundary decision).
- **`#170` (registry/docs/AI metadata)** adds the `table` registry entry (and any new transitive entries) to `registry/registry.json` and the public barrel (`packages/ui/src/index.ts`), following the existing multi-file-per-entry schema `overlay-runtime`/`popover` already use, and updates `docs/compatibility-matrix.md`/AI metadata only if a new runtime dependency is actually introduced (none is anticipated by this ADR).
- No existing BeeUI public API changes as a result of this ADR; it only decides the shape of a not-yet-implemented component family.

## Verification plan

- **Deterministic contract evidence**: unit/contract tests per subcomponent (roles/names/states on both the Web and native files), a stacked-mode column-label-inference test plus an explicit-`label`-override test, an RTL column-order test using `useDirection()`'s existing injectable seams, and a dynamic-type stress test confirming no `allowFontScaling={false}` is introduced (`docs/dynamic-type.md`'s existing repo-wide scan already enforces this for any new file under `packages/ui/src/components`).
- **Browser interaction evidence**: a new Table scenario in `apps/visual-regression/src/a11y-scenarios.ts` scanned by the existing axe-core gate (`docs/web-accessibility-audit.md`); Playwright keyboard/semantic checks that the header sort control is reachable by normal tab order and that `aria-sort`/`<th scope>` are present and correct.
- **Native runtime evidence**: iOS Simulator/Android Emulator VoiceOver/TalkBack evidence for row/column/header announcement and for both the `scroll` (horizontal `ScrollView`) and `stacked` presentations, per `docs/beeui-1.0-evidence-classes.md`'s assistive-technology evidence class — not compile-only evidence.
- **Visual evidence**: representative screenshots for `scroll` and `stacked` layouts, light/dark, LTR/RTL, at `#169`.
- **Performance evidence**: real (not fabricated) 100-row and 500-row measurements produced by the `#179` harness at `#168`, evaluated against whatever budget `#185` sets; this ADR does not itself state a numeric target, consistent with the harness's own no-fabrication design (`scripts/benchmark/scenarios/native/list-render.mjs`'s explicit "deferred off-device... never fabricated" contract).
- This ADR itself ships no code; its own self-test is doc-only.

## Revisit trigger

Revisit this ADR if any of the following become true with concrete evidence:

- `#168`'s real harness measurement shows the default (non-virtualized, non-adapter) render fails an accepted 100/500-row scale envelope — this would trigger designing the virtualization adapter (not silently defaulting to it), including resolving the `<table>` `aria-rowcount`/`aria-rowindex`/fixed-column-width requirement this ADR flags but does not solve.
- `#167`'s native accessibility investigation finds RN's available accessibility roles (on the pinned or a later RN version) provide a materially better native table/grid semantic than plain `View`/`Text` composition with row/column context folded into accessible names — that finding should update this ADR's native-strategy section with the verified role mapping rather than silently diverging from it in `#167`'s own implementation.
- A concrete, evidenced product requirement emerges for in-cell keyboard navigation/editing (the spreadsheet-style non-goal this ADR excludes) — that would need its own scoped ADR-style decision, not a silent expansion of `#165`'s implementation.
- The production demo (`#260`) or a real external consumer demonstrates the `layout="stacked"` column-label-registration mechanism is insufficient for a realistic header shape (e.g., grouped/multi-row headers) — that would need its own follow-up decision on multi-level header support, out of scope here.

## `#168` resolution (performance/scale acceptance)

`#168` registered `web/table-render-100`, `web/table-render-500`, and `web/table-row-update` (`scripts/benchmark/scenarios/web/table-render.mjs`) plus their deferred native counterparts (`scripts/benchmark/scenarios/native/table-render.mjs`), per this ADR's "Implementation consequences" above. Real, harness-measured evidence (`pnpm bench:web`) shows the default (non-virtualized) render costs well under 1ms per full render pass at both 100 and 500 rows on a representative dev host — comfortably inside a 16ms frame budget. **This confirms Option B stands as decided: no virtualization adapter is currently justified.** The revisit trigger above (an accepted envelope failing) has not occurred.

`#168` also empirically verified (`apps/showcase/__tests__/table-performance.test.tsx`) that `Table`'s compositional, no-owned-state design means a plain `rows.map(...)` re-runs every row's render function on any sibling's selection/sort change — Table does not implicitly memoize rows — and that wrapping row content in `React.memo` is a real, verified mitigation for consumers with very large lists. Documented for consumers in `apps/docs/src/content/docs/components/table.md`'s Performance section.
