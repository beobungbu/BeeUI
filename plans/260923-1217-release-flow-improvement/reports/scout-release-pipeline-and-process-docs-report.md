## 2. Branch / promotion model

**Web deployment** (`docs/beeui-web-deployment.md`) is a clean three-tier model: `development`→dev Worker, `staging`→stg Worker, `main`→production Worker, each via `beeui-web` (build) + `beeui-web-delivery` (deploy). This part of the docs matches the workflow triggers exactly.

**Package release** is different and is where the docs and reality diverge:

- `docs/npm-release-bootstrap.md:19` and `:72` both say "freeze the exact candidate on `main`" as the starting step for an RC, implying a release branch should land directly on `main`. Reality (confirmed by `gh pr view`/`git log`, see §3) is: a `release/<version>` branch is opened, PR'd into **`development`** first (e.g. PR #528, #622), then a **separate** `development`→`main` "promote to main" PR is opened and merged (e.g. #530). For `0.86.2-rc.1` this promotion PR chain ran **three times** (#530, #533 "hardened", #538 "hardened" again) before the SHA that was actually bootstrapped (`ddf415b0…`) existed on `main` — none of the release docs mention this iterative hardening loop.
- `docs/rc-candidate.md:15-20` records only the first promotion (`0b46eac…` for #528, `11c357…` for #529) as the "frozen candidate," predating the two subsequent hardening promotions. See §4 for why this is a live contradiction, not just an omission.
- `main` branch protection (`docs/release-ruleset.md:50-54`) requires 5 status checks, linear history, no force-push; **no required approving review count** (`requiredApprovingReviewCount: 0`, `release-ruleset.md:24`) — combined with `CONTRIBUTING.md`'s "No self-merge" rule (a **process** rule, not a branch-protection setting) and `require_code_owner_reviews` being off "while BeeUI has only one maintainer" (`release-ruleset.md:100`). This means "no self-merge" is currently a documented convention, not a GitHub-enforced control — nothing in the ruleset JSON blocks the PR author from clicking merge.
- Owner/manual steps vs automated: `docs/beeui-1.0-owner-gates.md` and `docs/agent-execution-contract.md` both draw the line at (a) `environment: release` approval on `bootstrap-rc`/`stage-rc`/`stage-stable`/`verify-stable`, (b) npm 2FA approval of each staged package, and (c) the final `latest` dist-tag move, which `docs/release-ruleset.md:88` and `docs/npm-release-bootstrap.md:96-100` both state is **manual only** because "npm Trusted Publishing/OIDC authenticates publish/stage-publish, not dist-tag mutation." Everything else (branch merges, version bump PRs, CI gates) is agent/human-authored PRs under the normal "no self-merge, independent review" rule in `CONTRIBUTING.md` and `docs/agent-execution-contract.md:15-28`.
- `docs/beeui-1.0-owner-gates.md:36-40` (#205) and `CONTRIBUTING.md` ("this repository remains private... do not publish packages/CLI/releases") both still read as pre-publication guidance. Reality: bootstrap-rc already ran and published four public packages on 2026-09-09 (`docs/dist-tag-policy.md:5,56-64`, `CHANGELOG.md:9-13`). `CONTRIBUTING.md`'s license/private-repo framing was not evidently updated after that event — a stale-doc gap (see §7).

## 3. Changesets

- `.changeset/config.json`: `fixed: [["@beemvp/beeui-ui","@beemvp/beeui-core","@beemvp/beeui-tokens","@beemvp/beeui-cli"]]`, `baseBranch: "development"`, `commit: false`, `access: "public"`, `updateInternalDependencies: "patch"` — all four public packages are one fixed group (matches ADR-011 D6 and `docs/release.md`'s lockstep rule).
- `.changeset/README.md` documents a 5-step manual cut: `pnpm exec changeset version` → `pnpm version:sync` → hand-edit the `dist-tag-policy` block + `consumer-compatibility-report.md` → `release-control-plane:check`/`web:check`/`docs:surface:acknowledge` → "Publication stays owner-gated (#254)." It does **not** mention `pre.json`/prerelease mode anywhere.
- **No `.changeset/pre.json` exists** in the repo, meaning Changesets is not in prerelease ("pre") mode even though the live version (`0.86.2-rc.1`) is itself a prerelease and the whole release scheme is built around a `0.86.2-rc.N` regex the npm-release workflow enforces (`npm-release.yml:91`). Running `pnpm exec changeset version` today, with no pre-mode entered, would not know to emit another `0.86.2-rc.N` — the standard Changesets prerelease workflow (`changeset pre enter <tag>`) is simply absent from this repo's process.
- Only one real changeset file exists: `.changeset/consumer-audit-batch.md`, declaring `minor` bumps for `@beemvp/beeui-ui` and `@beemvp/beeui-tokens`. `git log --oneline -- .changeset` shows exactly two commits touching the directory: `4f322cd` ("chore: track breaking changes with changesets and a public-surface inventory diff (#510)" — introduces the tooling) and `625c633` ("chore(changeset): minor bump for consumer-audit batch public surface additions"), authored `lantranduc@gmail.com`, **2026-09-18** (not 2026-09-21 — verified via `git log --format="%h %ad %s" --date=short -- .changeset/consumer-audit-batch.md`).
- **Contradiction**: `.changeset/consumer-audit-batch.md` declares `minor`, which under normal (non-fixed-major-0) semver would target `0.87.0`. ADR-015 fixes the stable line at `0.86.2` (`docs/decisions/015-package-version-0-86-2.md:16`), `docs/dist-tag-policy.md`'s machine-checked block pins `currentVersion: "0.86.2-rc.1"` / `candidateStableVersion: "0.86.2"` / `prereleaseVersionPattern: ^0\.86\.2-rc\.(0|[1-9][0-9]*)$` (`dist-tag-policy.md:108-122`), and `npm-release.yml`'s guards hard-fail any version that isn't `0.86.2-rc.N` or exactly `0.86.2`. Running `pnpm exec changeset version` on this changeset as written, with the workspace still on `0.86.2-rc.1` and no pre-mode active, would produce a version the release control plane cannot accept — the changeset and the version-pinning machinery are not currently compatible; nobody has run `changeset version` since `625c633` landed to discover this (confirmed: `packages/ui/package.json` is still `0.86.2-rc.1` at `HEAD`, and the newer `release/0.86.2-rc.2` branch bumps it by hand, not via `changeset version` — `git show origin/release/0.86.2-rc.2:packages/ui/package.json`).
- `CHANGELOG.md`'s `## Unreleased` section (`CHANGELOG.md:5-7`) still reads "No unreleased consumer-facing changes are recorded after the first public release candidate yet" even though `consumer-audit-batch.md` (merged 2026-09-18) and the already-merged Toolbar feature (`b40e603`, 2026-09-18) are exactly the kind of consumer-facing addition `docs/release.md:182-184` requires a changelog entry for — the changeset was never converted into a changelog entry because `changeset version` has never run against it. `CHANGELOG.md` is otherwise hand-authored (the `[0.86.2-rc.1]` entry, `CHANGELOG.md:9-31`, was clearly written manually, not generated by `changeset version`, since Changesets was not wired into the actual publish flow).

## 4. ADRs

`docs/decisions/` contains 15 ADRs (001–015): 001 styling engine, 002 overlay split, 003 native measurement timeout, 004 direction/RTL, 005 tooltip contract, 006 sheet gesture engine, 007 table/DataTable, 008 date/time, 009 Slider not-required, 010 adaptive Select not-required, **011 public distribution architecture**, 012 granular subpath exports, 013 demo app architecture, 014 public site Worker architecture, **015 package version 0.86.2**.

- **ADR-011** (public distribution architecture): D1 publishes all three library packages as public scoped packages (tokens included, previously private — needed so the source-ownership CLI can declare `@beemvp/beeui-tokens` as a real dependency, fixing issue #355's dangling-import gap). D2 built-output-primary (ESM+CJS+`.d.ts`), source-ownership stays a parallel path. D3 dual ESM/CJS. D4 `exports` conditions for RN/Metro/Web including a `react-native` condition and `theme.css` subpath. D5 lockstep coexistence of centralized-install and copy-source models. D6 lockstep versioning via a Changesets fixed group (explicitly names Changesets as the mechanism — this is the origin of `.changeset/config.json`'s `fixed` array). D7 npm provenance via OIDC + clean-consumer verification. Explicit owner guard: "no package or CLI is published... until the owner explicitly commands the BeeUI 1.0 release (#254)" — this framing (publication-ready-only) is now stale relative to the completed `bootstrap-rc` publish.
- **ADR-015** (package version 0.86.2): owner decision 2026-09-06, supersedes the `20260902.0.0` date-version scheme from #407. States plainly: "Subsequent versions follow SemVer. The bump is decided by changesets and a public-surface inventory diff, introduced separately in PR #510" (`015…md:25`). This is the direct textual source of the `minor`-bump contradiction in §3 — the ADR hands version-bump *decisions* to Changesets' semver classification, but the release machinery (npm-release.yml regex, dist-tag-policy pin) still hard-codes the `0.86.2` family with no visible mechanism for how a legitimate `minor`/`major` changeset is supposed to reconcile with that pin once `0.86.2` stable actually ships. No ADR addresses what happens after stable `0.86.2` publishes and a real `minor`/`major` changeset needs a new version line — this is an unresolved architecture gap, not just a doc bug.
- No ADR explicitly governs "distribution channels" as a topic distinct from ADR-011 (dist-tag mechanics live entirely in `docs/dist-tag-policy.md`, which is machine-checked but not an ADR); no ADR documents the "docs truth" pattern (`rc-candidate.md` vs `dist-tag-policy.md` diverging) — that pattern is undocumented and, per §2/§3, has already produced a live contradiction: `docs/rc-candidate.md` records the **frozen candidate SHA as `58d038d`** (2026-09-07, "refactor(release): remove unscoped digest recorder" — an ancestor of `0b46eac`) and ships SHA-256 hashes for tarballs built from that tree (`rc-candidate.md:28-33`), but the package that is actually live on the npm registry was built from `ddf415b0` (2026-09-08, PR #538) — ten commits later, including `fix(release): canonicalize publish manifest artifacts`, `fix(release): make canonical tarballs deterministic`, and `fix(release): serialize reproducibility builds`. `docs/release.md` and `docs/dist-tag-policy.md` correctly cite `ddf415b0` as the bootstrap SHA; `docs/rc-candidate.md` — the file whose stated job is to be "the human release-candidate authority" with retained checksums — was never updated after the two later "hardened" promotion PRs and now documents a different artifact than what is actually published.

## 5. Release-adjacent scripts

- `scripts/verify-release.mjs`: builds `packageSpecs` for all four packages, asserts required packed files exist per package (source + `dist/module`/`dist/commonjs`/`dist/typescript/{module,commonjs}` — dual ESM/CJS/.d.ts per ADR-011 D2/D3), extracts and checks manifests/exports/no-`workspace:*`, writes `.artifacts/release-verification.json`. Driven by `EXPECTED_VERSION` imported from `scripts/check-release-control-plane.mjs`. Honors `BEEUI_VERIFY_SHA` env for CI evidence tagging. Invoked by `pnpm release:verify` (`package.json:85`, chains `add-artifact-digests.mjs` after).
- `scripts/pack-artifacts.mjs`: explicitly documented (`:1-7`) as **not** a second build/pack authority — it only copies the exact byte-identical tarballs `release:verify` already produced from `.artifacts/release-packages/` into `.artifacts/pack/` for CI retention, never rebuilds. Run by `pnpm pack:artifacts` (`package.json:86`), invoked in `ci.yml:340` only when `github.event_name != 'pull_request'` (i.e. push/dispatch, not on PRs — PRs get `verify-release` without the pack step).
- `scripts/sync-root-version.mjs`: copies the version from `packages/ui/package.json` (the Changesets-writable source) onto `package.json` (root, private/non-workspace-member), `web/worker/package.json`, and the two Expo `app.json` identities (`apps/demo`, `apps/showcase`) — because `changeset version` cannot reach any of those four files. Run by `pnpm version:sync` (`package.json:112`); `release-control-plane:check` fails until this has run, per its own inline comment.
- `scripts/release/add-artifact-digests.mjs`: canonicalizes each raw `pnpm pack` tarball via `tar -xzf` → manifest canonicalization → **GNU-tar-only** `tar --sort=name --format=gnu --mtime=@0 --owner=0 --group=0 --numeric-owner -cf ... ` (`add-artifact-digests.mjs:214-223`) then `gzip -n -9`. `--sort=name` and `--format=gnu` are GNU tar extensions not supported by BSD tar (macOS's default `/usr/bin/tar`); this script is safe on `ubuntu-latest` CI runners (GNU tar) but will fail or silently behave differently on a contributor's Mac unless GNU tar (`brew install gnu-tar`) is installed and aliased — this is the "GNU tar" platform assumption the task flagged, and it is not documented anywhere in `CONTRIBUTING.md`'s local-setup section.
- `scripts/release/canonicalize-publish-manifest.mjs`: strips key ordering noise from the packed `package.json` before hashing, so the canonical tarball's manifest is comparison-stable.
- `scripts/check-release-control-plane.mjs`: exports `EXPECTED_VERSION` (the single source of truth read by `verify-release.mjs`, `pack-artifacts.mjs`, `add-artifact-digests.mjs`, and `npm-release.yml`'s expected-version guard). Run by `pnpm release-control-plane:check` (also runs `check-public-surface-ownership.mjs`).
- `scripts/check-release-ruleset.mjs`: the machine-checked contract behind `docs/release-ruleset.md`'s embedded JSON block, run in `verify-fast` (`ci.yml`) via `release-ruleset:check`/`:test` — this is the mechanism that keeps that doc's required-check list honest against the real `ci.yml` topology.

## 6. Comparison baseline (general knowledge, not repo evidence)

A typical Changesets-based OSS monorepo flow: contributors add a `.changeset/*.md` per PR; `changesets/action` runs on every push to the default branch, opens/updates a standing **"Version Packages" PR** that runs `changeset version` (bumps + writes `CHANGELOG.md`) whenever changesets are pending; merging that PR triggers the same action's `publish` step, which runs `changeset publish` (or a custom `pnpm publish` chain) with npm provenance/OIDC, and `changesets/action` tags each published package (`<pkg>@<version>`) and optionally opens GitHub Releases. Prereleases use `changeset pre enter <tag>` (e.g. `rc`) to switch every subsequent `changeset version` into `x.y.z-rc.N` output until `changeset pre exit`. Version bump size is decided by the changeset's declared `patch`/`minor`/`major` per package, not by a hand-maintained regex.

`release-please` (Google) instead derives version bumps and changelog entries from Conventional Commit messages on every push to main, maintains a standing "release PR" that when merged tags the release and (optionally) publishes; no per-PR changeset file is authored by hand. `semantic-release` runs fully in CI on every push to a release branch: analyzes commit messages, computes next version, publishes to npm, creates a git tag and GitHub Release, and writes the changelog, all in one CI run with no human-authored version-bump file and no separate manual promotion step.

BeeUI's flow differs from all three references in a specific way worth naming for the redesign: it has adopted Changesets' *file format and fixed-group config* (ADR-011 D6) but not its *automation* (no `changesets/action`, no generated "Version Packages" PR, no `changeset publish`, no tags/Releases from any workflow) — version bumps, `CHANGELOG.md` entries, and the four follower manifests are all still hand-driven via `.changeset/README.md`'s 5-step manual recipe, and the actual registry mutation runs through a hand-built `workflow_dispatch` state machine (`npm-release.yml`) rather than Changesets' own publish step.
