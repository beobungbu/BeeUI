## 6. Workspace/candidate version vs. published-on-npm version — where conflated

These are two genuinely different facts: (a) *what version this commit's manifests declare* (workspace/candidate version — always true, no network involved), and (b) *what npm's registry actually has published, and which dist-tag(s) point at it* (an external, time-varying observation that can only be *recorded*, never derived from the repo alone). Places that conflate them:

1. **`docs/dist-tag-policy.md:110-111`** — a single JSON block carries both `published` (an npm-registry fact) and `currentVersion` (a workspace-manifest fact) as sibling keys with equal authority, with nothing distinguishing "I observed this on npm" from "this is what the manifests say." `check-public-doc-truth.mjs:158-159` then asserts `policy.currentVersion === workspaceVersion` — i.e. the doc is required to always describe the workspace's *current* commit, never a *previously published* one, which forecloses ever documenting "workspace is at rc.2, npm still only has rc.1."
2. **`docs/consumer-compatibility-report.md:65,67`** — same pattern: `published` (registry fact) and `candidateVersion` (manifest fact) as siblings, cross-checked only against `docs/dist-tag-policy.md`'s `published`, never against a live registry probe.
3. **`scripts/generate-docs-foundation.mjs:180-213,362-364`** — `buildReleaseState` computes `currentVersion` (from the pin, nominally a registry-observation field) and `workspaceVersion` (from `package.json`) as two named-distinct fields in the same object, and then `validateDocsFoundationManifest:362` makes it a **hard CI failure** for them to differ. This forces the "two facts" model back into "one fact" by construction — the schema has room for divergence (a released rc.1 while workspace has moved to rc.2-dev) but the check forbids ever using it.
4. **`scripts/check-release-control-plane.mjs`'s `EXPECTED_VERSION`** (`:23-29`) is defined as "the pin from `docs/dist-tag-policy.md`" specifically *because* (per its own comment, `:10-14`) reading it from `package.json` "made every comparison against the root a tautology." This is a documented prior conflation that was partially fixed — but the fix still compares manifests to a hand-maintained doc field named `currentVersion`, which itself is asserted equal to the workspace version by `check-public-doc-truth.mjs` (point 1), so the tautology is reintroduced one hop away.
5. **`docs/dist-tag-policy.md`'s prose** ("Real current dist-tag state: `latest` also resolves to the RC") documents the registry-observation half reasonably carefully in prose (distinguishing "observed" from "deliberately promoted"), but this careful distinction exists **only as prose**, not as separate machine-readable fields — the JSON block itself has one `published: true` and one `currentVersion`, with no field for "as last observed on `<date>` via `npm view`" vs. "as of this commit."
6. **`web/worker/src/index.mjs:22-38` / `build-identity.json`** — `/api/health` reports `readWorkspaceVersion()` (workspace fact) under the unqualified key `version`, with no `published`/`npmVersion` field at all, so a consumer of the live API cannot tell whether the reported version is actually installable from npm.
7. **`scripts/check-distribution-policy.mjs:100-102`** ("a published prerelease must use the `next` channel") is the one place that treats `published` as a genuine registry-state gate on prose (forcing RC install commands onto `@next`), but it still derives "published" from the same hand-maintained boolean as everywhere else — there is no code path anywhere in this repo that calls `npm view` / hits the registry to verify `published` is actually true.

## Unresolved questions for the architect

- Is there any intent to add a real `npm view` registry probe (even a periodically-run one) to *populate* `published`/`currentVersion` from observation, or will it stay a manually-attested field indefinitely?
- Should `docs/dist-tag-policy.md`'s `currentVersion` be split into two fields (`workspaceVersion` and `lastPublishedVersion`) now that `generate-docs-foundation.mjs` already has both concepts but is forced to keep them equal?
- `apps/docs/src/lib/release-state.ts` is fully wired (generated JSON, typed contract, helper function) but unused by any page — is it dead scaffolding to remove, or the intended single source of truth that page work simply hasn't caught up to yet? If the latter, the 62 generated component pages and the `llms*.txt` family should probably be migrated to read `release-state.json` instead of independently calling `extractPublicationPolicy`/`readPublicationState` a third and fourth time.
