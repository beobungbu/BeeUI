# WS-L · fix #584: Sheet renders nothing on iOS (gorhom BottomSheetModal + BeeUI ModalOverlayHost)

Evidence and bisect: reports/ws-k-report.md (read fully, including the raw-gorhom variant table and the Maestro flow used to tap the trigger). Root cause isolated by WS-K: a plain `BottomSheetModal` with `snapPoints=['90%']`, `enableDynamicSizing={false}`, `BottomSheetView style={{flex:1}}` renders; wrapping the same content in a `StyleSheet.absoluteFill` View — the boundary `ModalOverlayHost` puts between `BottomSheetView` and BeeUI's content — makes it render nothing. Without `flex:1` on `BottomSheetView` nothing renders either, so `contentFill` must stay.

Owned: packages/ui/src/components/{sheet.native,overlay-transport.native,overlay-runtime,overlay-host-mode}.ts(x) (only what the fix needs), apps/showcase/** (native smoke fixture; remove the dev-only raw-gorhom bisect variants WS-K added once the fix is proven, keep the Sheet demo `onOpenChange` log only if a test uses it), apps/showcase/__tests__/**, .maestro/** or wherever native smoke flows live (check apps/showcase and .github/workflows/runtime-native.yml for the existing Maestro flow layout), plans/260919-1258-consumer-audit-followups/reports/**.

Steps:
1. Read how `ModalOverlayHost` lays out the sheet content on native and why it uses `StyleSheet.absoluteFill` (git log -S absoluteFill on the file explains the original intent; keep whatever that intent protects, e.g. keyboard/inset handling or measurement, but stop using an absolute-fill box inside `BottomSheetView`). Prefer `flex: 1` layout that gives the sheet content an intrinsic height, or move the absolute-fill layer outside `BottomSheetView`.
2. Prove the fix on the iOS Simulator the same way WS-K did (Node 24.13.1 from ~/.nvm, `export LC_ALL=en_US.UTF-8 LANG=en_US.UTF-8`, do NOT run `expo start` with CI=1, tap via the Maestro flow — the Simulator MCP `tap` did not reach the trigger).
